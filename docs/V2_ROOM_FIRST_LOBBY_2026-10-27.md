# Foundation V2｜共通ルーム先行・ゲーム切替ロビー（2026-10-27）

## 確認済みのユーザー要望
- 各ゲームに個別の部屋を作るのではなく、**先に1つのルームを作り、友達が集まった後にゲームを選ぶ**。
- 対局終了後は同じルームに戻り、入り直さず次のゲームを選べる構成とする。
- ユーザーはこのUXイメージを2026-10-27に明確に承認した。
- 学校iPad Safari、Google Sitesのコード直接埋め込み、無料、友達だけで遊ぶという従来の前提を維持する。

## ユーザー体験（確認済み要件と推奨案の区別）
1. 起動画面で「COMと遊ぶ」または「友達と遊ぶ」。COMではルーム不要（推奨）。
2. 友達と遊ぶ場合、ゲーム種別を指定せず共通ルームを作成/ルーム番号から参加。
3. ロビーでメンバーを確認し、ババ抜き・七並べ・神経衰弱・大富豪からゲームを選択。
4. 共通ルーム内で選んだゲームを遊び、対局結果後に同じルームへ戻る。
5. ルームを退出するまでは同じメンバー/番号を維持する。次のゲームに移っても部屋の作り直し不要。
- ゲームを誰が選ぶか、Ready操作、ルームの人数上限、2人ゲーム中の待機者扱いなどは未確定。実装前に整合性を検討し、必要なものだけ相談する。

## 設計方針
- 永続する **Room** と各ゲームの **Match** を分離する。Room: roomCode, members, host, chat, lobbyState。Match: matchId, gameId, participants, round, phase, authority, public/private views。
- ルーム作成時には gameId を固定しない。選んだゲームでMatchを新規作成し、終了後はMatchのみ破棄/終了する。
- ルーム・入退室・ゲーム選択・準備・結果・再戦は共通GameShell、盤面は既存V2 Game Registryと共通Table Rendererを再利用する。
- 既存の旧通信処理は game に紐付いたルーム作成 (`createFirebaseRoomHost({roomCode,game})`, `store.reserve(room,game)`) を前提にしているため、そのままのUI移植はしない。先にRoom/Matchの責務を切り分ける。
- 新しい試合への切替時に古い試合のコマンドが実行されないよう matchId/epoch とrevisionを照合する。秘密の手札、ルーム権限、通信中断時の操作制御を守る。
- ババ抜き・七並べ・大富豪は既存4人戦、神経衰弱は既存2人戦。共通ルームとマッチ参加人数を別概念とし、2人戦を選んだ際の余剰メンバーの取り扱いは未確定事項として残す。

## 改訂した優先順
1. 共通ルームの状態遷移とRoom/Match契約を先に定義し、純粋関数の単体テスト。
2. 共通ルームからババ抜きMatchを開始し、既存Firebaseホスト権限と新V2 Room Session/Rendererを接続。
3. 同じルームで試合終了→ロビーに戻る→別ゲームを選ぶ遷移をエミュレーター＋ブラウザ複数端末で確認。
4. 他の4人ゲームと神経衰弱2人戦へ展開。COM/オンラインで同じカード盤面。
5. 通信回数、操作反映速度、再接続、描画回数と学校iPad Safariの実機を検証する。
