# トランプコレクション｜オンライン・ゲーム拡張ロードマップ（2026-10-25）

## 正式なプロジェクト目標（オーナーの方針）
**定番の既存カードゲームを1つのゲーム集へ追加し続け、友達同士が学校のiPad（Safari）からオンラインで遊べるようにする。**
現在の4ゲームは第一弾であり、COM専用ゲーム集を完成形としない。COM対戦は一人用の選択肢として維持。

- 学校側の実利用・Google Sites版: **HTML/CSS/JSをGoogle Sitesに直接埋め込む**。GitHub Pages URLの埋め込みは正式配布方法ではない。
- GitHub Pages: **オーナーが自宅のPC/スマホで試遊するための別URL**。現行の通常版を勝手に上書きしない。
- 身内同士で無料運用。ログイン操作を要求しないことを目指す（バックエンドの匿名認証を使う場合は技術実装のみ）。
- 主に横向きタッチ操作・旧Safari・無音前提。
- オンライン実装前のCOMモードを残し、ルーム制御・通信の問題がCOMモードの安定性を壊さないようにする。
- 新ゲーム追加は原則として既存カードゲームのルールに基づく。独自に複雑化するより、分かりやすく何度も遊べることを優先。
- 既存ゲームの著作権・商標を尊重し、独自アート・名称を使用。過去の引き継ぎで「UNO」の名称・デザイン不使用は確定済み。

## Phase 9｜最新の進捗（2026-10-25）

[4ゲーム統合メニュー](ONLINE_COLLECTION_PHASE9_2026-10-25.md)を独立開発版として実装。COMと友達の2方式×4ゲームを単一HTMLで起動。自動テスト67件とChromium8モード検証に成功。**Firebase3ゲームの本番実通信は依然未設定**で、神経衰弱はSupabase身内用試作。学校の公開版は更新しない。次は実Firebaseの分離環境・アクセス制御の準備を優先。

## 2026-10-25 最新方針：身内用のため再読み込み復元は省略

- **ページ再読み込み／ブラウザ終了後の同じ対局・席の復元は不要**。完全な状態バックアップや匿名UID永続化は開発しない。新しいルームを作って遊び直せればよい。
- **一時的な通信断は別**：ページが開いている間は安全に停止し、復旧したら元の対局へ戻る既存の処理を維持。
- ホスト離脱時は終了案内と作り直しの導線を優先。無期限に固まったままにしない。
- 優先順位は実Firebase接続の安全確認、既存4ゲームのオンライン統合、UI、ゲーム追加。
- 本資料内の旧「更新でも対戦維持」「復元を次に実装」と読める項目より、**この決定を優先する**。

## 優先順位（新しく確定）
1. **共通オンライン対戦の土台**を先に確立する。新ゲームも同じロビー・ルーム番号・参加者管理を使えること。
2. **既存4ゲームを友達とのオンライン対戦に対応**する。2人用の神経衰弱で接続検証してから、4人用のババ抜き→七並べ→大富豪へ広げる。順序は開発上のリスクで調整可能。
3. **既存ゲームの選択ルールを拡張**する。特に大富豪の追加ローカルルールは基本モードと個別ON/OFFで分離し、ルールごとに自動テストを追加。
4. **新しい定番カードゲームを継続追加**する。候補はダウト、スピード、ポーカー、戦争、ぶたのしっぽ等。実装順はオーナーの希望と必要人数、オンライン難易度で決定。スピードはリアルタイム競争で別の通信要件があるため初期オンライン移植対象にはしない。
5. 学校実機での操作感・友達との対戦を踏まえて改善し、版を確定する。

## オンラインの最小体験
- 入口: 「COMと遊ぶ」「友達と遊ぶ」。オンラインではルーム作成→短い番号の共有→友達が入力→人数が揃ったらホストが開始。
- 1ルームでゲーム・参加席・ルール設定・開始状態・現在のターン・結果・再戦を共有する。
- 2人用／4人用を同じ枠組みで扱える設計にする。必要人数と空席の扱いはゲーム別に明示し、混乱する自動COM補充は初期版に入れない。
- スマホ＋PCなどの別端末で接続テスト。一時的な回線切断・二重押し・古い操作・同時操作でもカード数が壊れない。**再読み込み後の対局復元は対象外**。
- 対戦の正本は1か所に固定する。単に各端末で `G.create...` や `Math.random()` しても配札や判定を共有できないので、決定したゲーム状態／手順番号を同期する。
- **公開状態と非公開手札を分ける**。全プレイヤーの手札・デッキの答えをそのまま全員に配信しない。共通状態には場札・手札枚数・ターン・順位など必要な情報のみ。個別の手札・神経衰弱の伏せ札などは、ゲームのルールに応じた読み取り範囲を別途設計する。
- ルーム番号は認証ではない。無料のFirebase Realtime Databaseなど既存プロジェクトの通信知見を候補とするが、実接続前に認証（必要なら匿名）、権限ルール、読み書き範囲、ルーム掃除、無料枠を検証する。**他ゲームの稼働中のDB・Rulesを勝手に変更しない**。
- ホストが配札・ターン判定を行う身内向け方式は第一候補だが、ホストに非公開情報が必要になる場合の限界を文書化する。厳格な不正対策が必要ならサーバー側の配札・判定を追加する（実装コストは別途評価）。
- Google Sites用 `dist` は**単一HTMLとして納品**。既存の「外部読み込みゼロ」はオフラインCOM版の制約として維持し、オンライン時は通信バックエンドへのHTTP/WebSocket等の通信が必要となるため例外を明確にする。可能なら外部のJS/CSSライブラリには依存しない。学校のネットワーク遮断有無は実機試験で確認。

## 推奨実装順
**A: 土台設計**
現在の `games.mjs`（各ルール）と `index.html`（描画とCOM進行）の責務を明確にする。新ゲーム追加時に巨大な1ファイルへ全部の分岐を増やさない構成を検討。既存の4ゲームが壊れないよう20件のテストとブラウザ回帰を基準にする。

**B: 最小オンライン試作**
新規独立の開発HTMLで「ルーム作成／参加／READY／開始／2端末表示一致」を試す。最初は神経衰弱2人で配札・ターン・カード2枚のめくり・再戦・再接続を完走。相手の非公開情報を除いた表示・操作を作る。接続失敗では原因を表示し、勝手にオフライン処理を進めない。

**C: オンライン横展開**
ババ抜き（カードを相手から引く。自分の手札のみ公開）、七並べ、大富豪の順に対応。全4ゲームで2〜4端末・最後まで・再戦・回線復旧を検証。

**D: ゲーム追加／ローカルルール拡張**
ゲームを追加するたびに「COMモード→ロジックテスト→オンライン接続→ブラウザ表示→単体HTML」の流れを繰り返す。ルール設定の同期とルールの一致も検証。

**E: 学校向け確定**
既存のGoogle Sites版はオーナーの実機試験・OKがあるまで変更しない。実機の通信品質と表示・入力を優先し、過剰な対戦履歴・リプレイ・会員登録などは増やさない。
