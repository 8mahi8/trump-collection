# Phase27｜学校iPad向け・実操作デバッグ（2026-10-26）

## 今回の目的
「自動テスト106件成功」という表現だけでは、学校の友達が**Google Sitesで実際にカードをタップして1手進められるか**は分からない。4画面のオンライン実験を、ゲームの手番に沿ったUIタップと全員への状態反映まで拡張した。

## 検証コードの変更
- `dev/verify-configured-sites-emulator.mjs` を拡張。環境変数 `TC_SITES_GAME=babanuki|shichinarabe|daifugo` を追加し、統合HTMLのメニューから**選んだゲームを起動**。4枚の独立したブラウザ画面は、Google Sitesを模した sandbox iframe、その内側にゲームの srcdoc iframe を使う。
- 4人参加、READY、開始後にホストの公開状態から現在の手番を調べ、**本当に手番のあるブラウザ**のカードを操作する。
- ババ抜き：引く相手の伏せカードを1枚タップ。
- 七並べ：自分の合法な札を選択→選択だけではrevisionが増えないことを検証→「選択カードを出す」で確定（出せなければパス）。
- 大富豪：合法手に含まれる札を手札から選択→選択だけでは確定しないことを検証→「選択カードを出す」で確定。
- **4画面すべてで公開revisionが1以上進むこと**、通信状態、800×450横画面で左右にはみ出ないこと、チャット受信、戻る操作後の残った3人の終了を確認。
- ゲーム画面に合わせて `hasTouch:true` でタッチ対応ブラウザを作り、カード選択・確定をPlaywrightの `.tap()` で実行する。これは**タッチイベントのエミュレーション**であり学校iPad実機と同一ではない。
- CIの現行公開ルール試遊版テストは**ババ抜き・七並べ・大富豪の3ゲーム×Chromium/WebKit**に拡大。通常認証版もババ抜きのタップ操作を両エンジンで検証。通信はすべてFirebase Local Emulatorへ転送し、**実本番データベースへは接続しない**。

## 失敗原因の切り分け
- 初回はテスト側で`frameLocator.evaluate()`を呼んでいたが、Playwright APIにそのメソッドはない。子iframe内の`body` Locator `.evaluate()`に変更。
- 次に、テストコードが`locator.evaluate(rev => ...)`と書いており、第1引数には`rev`ではなく**DOM要素**が渡されるため、常に`revision > DOM要素`の偽判定になった。正しい`(element, rev)`に修正。
- 調査時のCI診断では、ババ抜きの操作前`revision=8`から**4人全員が`revision=9`へ同期し、privateRevisionも全員9**であることを記録。**ゲーム本体の同期不良ではなくテストの観測バグ**と判明した。
- 変更はデバッグ用スクリプトとCIが中心。ゲームエンジンとFirebase本番ルールは変更していない。
